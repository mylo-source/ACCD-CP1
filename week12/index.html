Red Light, Green Light – Gesture-Controlled ML Prototype

● ▲ ■

Inspiration

This project is inspired by the “Red Light, Green Light” challenge ("무궁화 꽃이 피었습니다"-Mugunghwa kkochi pieotseumnida) from Squid Game. In the show, players advance toward a finish line but must freeze completely when a large doll-like machine turns around to detect movement.

In class, we explored Teachable Machine and ml5.js for webcam-based image classification. This week, I believe we are exploring gestures! This, in particular, made me want to build a version of the game where the player’s body becomes the only controller — no keyboard or mouse.

● ▲ ■

Concept Overview

When the Green Light symbol is on, players move their on-screen character towards the finish line by performing a specifically-trained Move Gesture in front of the webcam. Alongside this, users can visually hear the famous audio that accompanies the players in this challenge. Once the audio ends, the game switches to Red Light (green symbol turns off, red symbol turns on) and the player has to return to a Still Pose to avoid detection by the 'statue' at the top of the field.

Goal: Reach the finish line without being detected by the statue during Red Light.
● ▲ ■

How It Works (Game Rules)

Green Light

  • Green Light Symbol on
  • Audio plays
  • Statue faces away
  • Move Gesture made by player moves on-screen character

Red Light

  • Red light symbol on
  • Audio stops
  • Statue faces on-screen character
  • Player must hold Still Pose.
  • Any movement → immediate loss.
Win Condition: Reach the finish line during any Green Light phase.
● ▲ ■

Physical ↔ Digital Mapping

This game uses the player's body as the complete input system.

Physical Inputs

  • Move Gesture (maybe an arm raised?)
  • Still Pose (neutral posture)

Digital Output

  • Move Gesture → makes character moves upwards (Green Light only)
  • Still Pose → no movement
  • Movement during Red Light = loss

Technical Plan

1. Teachable Machine Model:

  • Move Gesture
  • Still Pose

2. Game States:

  • "green"
  • "red"
  • "win"
  • "lose"

3. Movement Logic:

  • Green + Move Gesture → move
  • Red + anything except Still Pose → lose

4. Visual Components:

  • Field + start/finish lines
  • Green Light & Red Light icons
  • Player icon (simple shape)
  • Statue (simple shapes; turns red or green based on state)
  • Webcam preview
  • Basic feedback messages (“You Win”, "You Lose")

5. Timing:

  • Green Light duration = duration of audio
  • Red Light duration = 3s
  • Cycles continue until win/lose

Iteration & Refinement – Week 2

With a solid technical and conceptual foundation in place, and after receiving feedback from my professor (Maxim), I decided to refine both the interaction logic and the interface of the prototype. Rather than expanding scope, I focused on stabilizing the system, with an emphasis on clarity and strengthening the overall look and feel of the experience.

One of the most significant changes involved rethinking how the player physically controls the game. Instead of relying on a single trained image-classification gesture for movement and a still pose for freezing, the prototype now uses ml5.js HandPose and BodyPose models for more direct and responsive control that works in any environment.

Specifically, the player now advances towards the finish line by pinching their thumb and index finger together, detected through HandPose tracking. To enforce the “freeze” mechanic during Red Light, the system tracks the player’s nose position via the webcam. Any detectable movement of the nose while the game is in Red Light results in an immediate loss. This shift allowed the interaction to feel a lot more embodied and responsive, while also reducing reliance on model training and environment calibration.

After implementing these interaction mechanics, I made the decision to remove the audio component of the prototype. Due to time constraints, I felt that I could not explore audio feedback with the depth it deserved. Instead, I pivoted focus to strengthening visual state feedback so that players could clearly understand when they were allowed to move and when they needed to freeze.

To support this, I introduced several interface elements that communicate game state without relying on text:

  • Red and Green Light indicators embedded in geometric forms
Green Light indicator — movement permitted
Red Light indicator — freeze required
  • Statue scanning behavior reinforcing surveillance
Statue facing away during Green Light
Statue scanning the field during Red Light
  • State-based glowing borders applied consistently
Idle state — neutral pink glow
Green Light — movement allowed
Red Light — movement detection active

Once the core interaction and feedback systems were stable, I focused on UI refinement and cohesion. This included applying a consistent Squid Game–inspired visual theme across the interface (shapes, color palettes, typography, and layout) — to create a more aligned experience.

Squid Game–inspired color palette and geometry

I also refined the game flow by introducing Start and Reset glowing buttons. In earlier iterations, the game began immediately upon page load, which left little room for players to understand the rules or prepare. By requiring the user to intentionally start the game, the experience now allows time for orientation and instruction-reading before interaction begins.

Start button — intentional game entry
Reset button — appears after win or loss
